# 计划：项目（用户创建，一级）→ 细分功能板块（二级）+ 记忆分层

## 概述

把工作台的导航从"两个固定板块"改成**以用户创建的项目为中心的四层结构**，并让记忆按层级共享/隔离：

```
项目（用户创建，如「水杯项目」）
 ├─ 选品           ← 区块：与 Listing 平级，只是视觉分区，不是层级
 │   ├─ 需求验证 ┐
 │   ├─ 竞争分析 ├─ 直接点击 → 该板块的功能对话窗口（二级）
 │   ├─ 利润测算 │      └─ 窗口内可切换本板块下的多段会话
 │   └─ 自由对话 ┘
 └─ Listing        ← 区块：与选品平级
     ├─ Listing 起草
     ├─ 图片合规自检
     └─ 自由对话
```

一句话：**只有二级** —— 项目（一级）→ 细分功能板块（二级，点进去就是对话窗口）；会话**不是独立一级**，而是在二级窗口内切换。

---

## 一、需求原文与澄清

用户原话（两轮）：

> 「有个地方要选择哪个项目，我是想把它放到中控台里面，点进去之后然后用细分的嘛，比如说什么 listing 还有什么选品，在里面之后才是二级分类，比如说，点进选品的价格竞争分析，里面还有的选，选择哪一个会话」

> 「那个选品和 listing 不是项目的内容，项目的内容是用户创建的，比如说创建一个关于水杯的项目，然后点进项目可以看到 listing 和选品的列表，然后点击列表，进入具体的细分功能的对话窗口，然后这里才是二级，就是在具体细分的功能的对话窗口下面是可以选择不同的会话的」

> 「一级会话下面的记忆都是共享的，只是说不同的二级会话共享的记忆部分不一样」

**关键纠正**：`选品` / `Listing` **不是项目**，**也不是中间的一级** —— 它们是**每个项目内部都有的、平级的两块区块**（界面上并排呈现，各自把底下的细分板块列出来）。项目本身是用户创建的、由具体商品/主题定义的容器（"水杯项目"、"充电宝项目"）。

**理解偏差记录**：第一版把"选品 / Listing"当成了两个并列项目，并把模块网格摊在总控台页上 —— 错在把**产线**当成了**项目**，也漏掉了"会话挂在功能之下"这一层。

---

## 二、层级模型（权威定义）

| 级别 | 名称 | 谁创建 | 基数 | 例 |
| --- | --- | --- | --- | --- |
| **一级** | **项目 Project** | **用户创建** | 任意多个 | 水杯项目、充电宝项目 |
| **二级** | **细分功能板块 Feature** | 系统固定（现有 11 个模块） | 每个项目 11 个 | 需求验证、竞争分析、利润测算 |
| 窗口内 | **会话 Conversation** | 用户新建 | 每个板块任意多段 | 同一板块下的"保温杯 vs 竞品价格带"等 |

**区块（非层级）**：`选品` / `Listing` 是**平级的两块**，只承担视觉分区与记忆标签的作用，**在导航上不占一级、也不是中间层**。界面沿用最早总览页的形态：两个区块并排，各自把底下的细分板块一起列出来，**直接点某个细分板块就进对话窗口**。

现有模块 key（`ui/app.js` 的 `BOARDS`，实现时以此为准）：

- 区块 `research`（选品）：`demand` / `competition` / `profit` / `supplier` / `report` / `free`
- 区块 `listing`（Listing）：`draft` / `image` / `price` / `fulfill` / `free`

> 命名澄清：所谓「**二级**」= **细分功能板块**。会话挂在板块的对话窗口内，通过窗口内的会话切换条选择，**不构成第三个导航级**。

## 三、界面与导航

### 3.1 两栏：左栏项目列 + 主区

```
左栏（项目）            主区 = 项目总览（沿用最早的形态）
┌──────────┐  ┌────────────────────────────┬────────────────────────────┐
│◆ 总控台   │  │ 01  选品                    │ 02  Listing                 │
│──────────│  │  ┌──────────┐ ┌──────────┐ │  ┌──────────┐ ┌──────────┐ │
│水杯项目  ✓│  │  │1.1 需求验证│ │1.2 竞争分析│ │  │2.1 起草   │ │2.2 图片  │ │
│充电宝项目 │  │  └──────────┘ └──────────┘ │  └──────────┘ └──────────┘ │
│＋新建项目 │  │  ┌──────────┐ ┌──────────┐ │  ┌──────────┐ ┌──────────┐ │
│          │  │  │1.3 利润测算│ │1.4 货源比价│ │  │2.3 定价   │ │2.4 履约  │ │
│          │  │  └──────────┘ └──────────┘ │  └──────────┘ └──────────┘ │
└──────────┘  └────────────────────────────┴────────────────────────────┘
                            ↑ 直接点某个细分板块 → 进该板块的对话窗口
```

- **左栏 = 项目列表**（用户创建）+ 底部「＋ 新建项目」；**总控台**是左栏顶部的**独立入口**（发丝线隔开，不占项目列表的位置）。
- **主区（项目总览）**：沿用**最早总览页**的形态 —— `选品` 与 `Listing` 两个**平级区块并排**，每个区块把自己底下的细分板块网格一起列出来，**直接点板块即可进入**。
- **主区（板块对话窗口）**：点板块后进入，沿用现有 `#view-module` 的「左侧表单 + 右侧对话流」。

### 3.2 会话选择的位置（在二级窗口内）

会话不是独立一级，所以**会话切换条放在板块对话窗口的顶部**：

- 顶部一条会话栏：显示**当前会话名** + 会话数 + 「＋ 新对话」，点开列出本板块的所有会话；
- 每条会话带状态点：进行中 / **有未完成断点** / 已结束（沿用已实现的 `has_open_interrupt` 数据，不需要新接口）；
- 切板块即切换到该板块的默认会话，切会话不改变所在板块 —— 这正是"只有二级"的交互体现；
- **会话归属固定为创建时所在的板块**（`session_id` 一旦落库就不再自动漂移），会话条的「⋯」菜单里给一个「**移动到其他板块**」，跨板块只能由用户显式操作一次。这样 L2 记忆层始终稳定（不随用户浏览动作漂移）；移动后按新板块过滤 L2。

### 3.3 项目的生命周期

| 动作 | 语义 |
| --- | --- |
| 新建项目 | 输入名称（可选描述）→ 生成 `project_id` → 自动显示两个区块与 11 个细分板块 |
| 重命名 / 改描述 | 只改元数据 |
| 归档（隐藏） | **归档 ≠ 删除**：项目及其下所有会话、记忆、断点全部保留，只是不出现在常规列表（可切换显示） |
| 删除项目 | **不提供** —— 与既有的「隐藏 ≠ 删除」契约保持一致；需要"消失"就归档 |

**同名项目**：允许（`project_id` 唯一，名称仅作展示；列表里显示创建时间辅助区分，不做重名校验、不阻塞用户流程）。

### 3.4 总控台（选 A：保留，且必须"有反应"）

总控台是**非项目的全局首页**，与「某个项目」并列在左栏顶部（发丝线隔开）。它不是一块空牌子，装**四块内容**：

```
┌ 总控台 ────────────────────────────────────────────────┐
│ ① 全局对话            │ ② 项目卡片                       │
│   不挂任何项目的通用问答  │   最近项目（名称/会话数/未完成    │
│   （scope=global，      │   断点）+ 「＋ 新建项目」          │
│   记忆只取 L0）         │                                  │
│─────────────────────┼──────────────────────────────────│
│ ③ 待办汇总            │ ④ 记忆与规则                       │
│   跨项目的未完成断点，   │   L0 全局记忆条目（只读预览）      │
│   点一条直接跳到那个会话  │   + 死规则（状态记忆）             │
└──────────────────────┴──────────────────────────────────┘
```

| 块 | 数据源（全部复用既有接口） | 点它的反应 |
| --- | --- | --- |
| ① 全局对话 | `POST /api/ask` 传 `scope=global`，**不带** `project_id` | 就在总控台页内对话；记忆只注入 L0（最小上下文，最干净） |
| ② 项目卡片 | `GET /api/projects`（已含 `session_count` / `open_interrupts` / `has_unfinished`） | 点卡片 → 进入该项目总览（两个平级区块 + 板块网格） |
| ③ 待办汇总 | `GET /api/interrupt/recent?status=open`（跨项目） | 点一条 → 直接跳到对应项目 + 板块 + 会话，并弹出续跑提示 |
| ④ 记忆与规则 | `GET /api/settings`（死规则）+ 记忆检视接口 | 只读展示；后续"待提升条目"（第 5 步）也挂这里 |

**为什么保留它**：① 是"干净的全局上下文"落点 —— 用户要的"换话题不污染"在总控台页天然成立（不挂项目 = 不注入 L1/L2）；② 是跨项目的唯一汇总视角（待办汇总），离开它就只能逐个项目点进去找断点。

## 四、记忆分层（本次核心）

### 4.1 四层

| 层 | 键 | 存什么 | 可见范围 |
| --- | --- | --- | --- |
| **L0 全局** | `user_id` | 死规则（状态记忆）、用户画像、跨项目事实、技能记忆 | 所有项目 / 所有板块 / 所有会话 |
| **L1 项目** | `project_id` | 项目级事实与偏好（目标市场、毛利红线、供应链约束、该项目常用类目）、项目级谈话总结 | 该项目下**全部**板块的**全部**会话 |
| **L2 板块** | `project_id + feature_key` | 该板块的结论与范式（价格带区间、竞品集、常用参数、常用 prompt 套路） | 同项目**同板块**的会话 —— **不回流到其他板块** |
| **L3 会话** | `session_id` | checkpoint 对话历史、中断断点（可续跑台账）、短期窗口 | 仅本会话 |

对应关系：用户说的"一级共享" = **L1 项目层共享**；"不同的二级会话共享的记忆部分不一样" = **L2 功能层各不相同**。

**区块（选品 / Listing）的定位**：**不参与记忆分层**。它只承担两件事：① 界面上的视觉分区（两个平级区块并排）；② 记忆条目的一个**说明性标签**（例：某条记忆属于 Listing 语境，便于展示与人工筛选）。记忆的共享边界只有「全局 / 项目 / 板块 / 会话」四种。

### 4.2 注入顺序

`L0 → L1 → L2 → L3`，**越具体越靠后**。

- 越靠近当前话题的块放越后面，模型注意力上更占优，避免被泛化的项目级/全局记忆盖住具体结论。
- 与现有 `core/perception/context.py::assemble_context()` 的块机制一致（现返回 `rules / resume / facts / kb_index / window_topics / hot_skills`）。
- 新增两个块：`project_memory`（L1）、`feature_memory`（L2），排在 `facts` 之后、`resume` 之前。

### 4.3 写入策略（易错点）

**默认写入最具体的一层（L2 功能层）**，再由总结管线判断是否提升：

| 判断 | 去向 |
| --- | --- |
| 只在本功能内成立的结论（如"这个品类的价格带是 89–129"） | 留在 **L2** |
| 跨功能复用、或用户明确说"以后都按这个来" | 提升到 **L1 项目** |
| 与具体项目无关的偏好（如"回答用中文、要表格"） | 提升到 **L0 全局** |

实现：在总结管线的输出里加一个字段 `promote_to: feature | project | global`（默认 `feature`），由管线写入对应层。
同时提供**手动提升**入口（"这条以后都按这个来"），避免只靠模型判断。

> 不做这一层判断的后果：模块级记忆各说各话 —— A 功能以为做日本站、B 功能不知道，项目级约束失去意义。

### 4.4 隔离规则（必须在检索层强制）

- 模块 A 的会话**看不到**模块 B 的 L2，但两边都看得到 L0 与 L1。
- 实现方式：记忆检索查询带上 `(project_id, feature_key)` 过滤 —— **不靠提示词约束**（提示词约束不可靠，且会把不该看的内容塞进上下文）。
- 中断台账（`interrupt`）与短期窗口天然是会话级（L3），无需改动。

## 五、数据模型改动

### 5.1 新表 `projects`

```sql
CREATE TABLE IF NOT EXISTS projects(
    project_id  TEXT PRIMARY KEY,      -- uuid4 hex
    user_id     TEXT DEFAULT '',
    name        TEXT DEFAULT '',       -- 水杯项目
    desc        TEXT DEFAULT '',
    status      TEXT DEFAULT 'open',   -- open | archived
    created_at  TEXT,
    updated_at  TEXT
);
```

### 5.2 `conversation_registry` 扩列（沿用现有迁移写法）

| 新列 | 说明 |
| --- | --- |
| `project_id` | 所属项目；空 = 未归档到任何项目 |
| `feature_key` | 细分功能 key（`demand` / `competition` / …） |

现有 `scope` 列**复用为区块标签**（`research` / `listing`，对应界面上的选品 / Listing 两块）。它只用于界面分区与展示，**不参与记忆隔离**，语义不变，无需迁移。

### 5.3 记忆条目标签

长期记忆 / 知识库条目增加 `project_id`、`feature_key` 两个标签位（加列，或写入既有 `metadata` JSON）。技能记忆保持全局（L0），不参与项目隔离。

### 5.4 老数据迁移

- 现有会话 `project_id` 为空 → 前端归到「**未分类**」分组，**不丢、可续跑**。
- 提供一次性"把未分类会话归入某项目"的入口（前端批量操作即可，后端只改列）。

## 六、接口改动

| 接口 | 类型 | 说明 |
| --- | --- | --- |
| `GET /api/projects` | 新增 | 项目列表（含每个项目的会话数、未完成断点数） |
| `POST /api/projects` | 新增 | 新建项目（`name` / `desc`） |
| `PATCH /api/projects/{id}` | 新增 | 改名 / 改描述 / 归档（**归档 ≠ 删除**） |
| `GET /api/projects/{id}/tree` | 新增 | 该项目下的区块 → 板块 → 会话数（一次返回，避免前端 N 次请求） |
| `GET /api/conversations` | 扩展 | 加 `project_id` / `feature_key` 过滤（`scope` 继续按区块过滤） |
| `POST /api/conversation/start` | 扩展 | 加 `project_id` / `feature_key`（`scope` 仍传区块） |
| `POST /api/ask` | 扩展 | 同上，透传到 `assemble_context` |
| `PATCH /api/conversations/{sid}` | 扩展 | 除 `title` / `hidden` 外，支持 `project_id` / `feature_key`（实现「移动到其他板块」） |
| `GET /api/guide` | 扩展 | 指导智能体的"导航状态"块加入项目 / 板块维度 |

约定：`/api/projects/{id}/tree` 一次返回整棵树，前端只拉一次即可渲染项目总览（避免逐级请求）。
